S4  CROSS-SHARD QUERIES - scatter-gather, and when aggregation can be pushed to the shards
====================================================================================================
   3.489s  [coordinator] (a) GROUP BY a column that is NOT the shard key:
   3.489s  [coordinator] SELECT status, count(*) FROM appointment GROUP BY status ORDER BY status
   3.499s  [coordinator] Finalize GroupAggregate
                           Output: appointment.status, count(*)
                           Group Key: appointment.status
                           ->  Sort
                                 Output: appointment.status, (PARTIAL count(*))
                                 Sort Key: appointment.status
                                 ->  Append
                                       ->  Partial HashAggregate
                                             Output: appointment.status, PARTIAL count(*)
                                             Group Key: appointment.status
                                             ->  Foreign Scan on public.appointment_s1 appointment
                                                   Output: appointment.status
                                                   Remote SQL: SELECT status FROM public.appointment_shard
                                       ->  Partial HashAggregate
                                             Output: appointment_1.status, PARTIAL count(*)
                                             Group Key: appointment_1.status
                                             ->  Foreign Scan on public.appointment_s2 appointment_1
                                                   Output: appointment_1.status
                                                   Remote SQL: SELECT status FROM public.appointment_shard
   3.661s  [coordinator] result: Cancelled=17,190, Completed=206,135, NoShow=24,184, Scheduled=47,992
   5.327s  [coordinator] median 163.6 ms. Remote SQL is a bare 'SELECT status': every one of the 295,501 values crosses the network and is partially aggregated on the coordinator (postgres_fdw in PG16 cannot push a PARTIAL aggregate to a shard).
   5.327s  [coordinator] (b) GROUP BY the shard key: each group lives on one shard, so the whole aggregate is pushed down:
   5.327s  [coordinator] SELECT patient_id, count(*) AS visits FROM appointment GROUP BY patient_id HAVING count(*) >= 20 ORDER BY visits DESC, patient_id LIMIT 5
   5.330s  [coordinator] Limit
                           Output: appointment.patient_id, (count(*))
                           ->  Sort
                                 Output: appointment.patient_id, (count(*))
                                 Sort Key: (count(*)) DESC, appointment.patient_id
                                 ->  Append
                                       ->  Async Foreign Scan
                                             Output: appointment.patient_id, (count(*))
                                             Relations: Aggregate on (public.appointment_s1 appointment)
                                             Remote SQL: SELECT patient_id, count(*) FROM public.appointment_shard GROUP BY 1 HAVING ((count(*) >= 20))
                                       ->  Async Foreign Scan
                                             Output: appointment_1.patient_id, (count(*))
                                             Relations: Aggregate on (public.appointment_s2 appointment_1)
                                             Remote SQL: SELECT patient_id, count(*) FROM public.appointment_shard GROUP BY 1 HAVING ((count(*) >= 20))
   5.404s  [coordinator] result: patient 31: 28, patient 24: 24, patient 26: 23, patient 53: 23, patient 33: 22
   6.031s  [coordinator] median 61.2 ms. Remote SQL contains GROUP BY ... HAVING: the shards aggregate in parallel (Async Foreign Scan) and only the qualifying groups are returned. Lesson: choose the shard key to match the heaviest queries.

S7  CROSS-SHARD TRANSACTIONS - postgres_fdw commits each shard separately (no two-phase commit)
====================================================================================================
   6.318s  [coordinator] UPDATE touching both shards committed: postgres_fdw opened a remote transaction on each shard and committed them
                         one after the other. If a shard failed between the two remote COMMITs, one change would persist and the other
                         would not. Citus and similar systems close this gap with two-phase commit (PREPARE TRANSACTION / COMMIT PREPARED).

R1  SLOT HOLD - a 5-minute lock while a receptionist completes a booking (SET NX EX)
==============================================================================
# Receptionist A opens the booking form for Dr Okafor's 09:00 slot:
127.0.0.1:6379> SET slot:hold:doctor:1:2026-11-04T09:00 receptionist-A NX EX 300
OK
# Receptionist B opens the same slot a second later - NX refuses because the key exists:
127.0.0.1:6379> SET slot:hold:doctor:1:2026-11-04T09:00 receptionist-B NX EX 300
(nil)
127.0.0.1:6379> GET slot:hold:doctor:1:2026-11-04T09:00
"receptionist-A"
127.0.0.1:6379> TTL slot:hold:doctor:1:2026-11-04T09:00
(integer) 300
# B is told 'slot being booked by another user'. A completes the booking in PostgreSQL
# (the EXCLUDE constraint is still the final guard), then releases the hold - but only
# if A still owns it. A Lua script makes check-and-delete atomic:
127.0.0.1:6379> EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 slot:hold:doctor:1:2026-11-04T09:00 receptionist-B
(integer) 0
127.0.0.1:6379> EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 slot:hold:doctor:1:2026-11-04T09:00 receptionist-A
(integer) 1
127.0.0.1:6379> EXISTS slot:hold:doctor:1:2026-11-04T09:00
(integer) 0
# If A's browser crashes, the hold simply expires after 300 s - no stale lock remains.

R4  CRITICAL LAB ALERTS - Redis Streams with a consumer group
==============================================================================
127.0.0.1:6379> XGROUP CREATE lab:critical on-call-clinicians $ MKSTREAM
OK
# The laboratory system appends one entry per critical result:
127.0.0.1:6379> XADD lab:critical * mrn WCB0013656 test TROP value 52.000 resulted_at "2026-10-28 19:09"
"1793225809941-0"
127.0.0.1:6379> XADD lab:critical * mrn WCB0028022 test TROP value 57.000 resulted_at "2026-10-28 16:58"
"1793225809941-1"
127.0.0.1:6379> XADD lab:critical * mrn WCB0009591 test TROP value 58.000 resulted_at "2026-10-28 13:41"
"1793225809941-2"
127.0.0.1:6379> XLEN lab:critical
(integer) 3
# Dr Fairbanks' pager app reads new alerts for its consumer:
127.0.0.1:6379> XREADGROUP GROUP on-call-clinicians dr-fairbanks COUNT 2 STREAMS lab:critical >
   1793225809941-0  mrn=WCB0013656  test=TROP  value=52.000  resulted_at=2026-10-28 19:09
   1793225809941-1  mrn=WCB0028022  test=TROP  value=57.000  resulted_at=2026-10-28 16:58
# One alert is acknowledged after the call-back; the other stays pending until handled:
127.0.0.1:6379> XACK lab:critical on-call-clinicians 1793225809941-0
(integer) 1
127.0.0.1:6379> XPENDING lab:critical on-call-clinicians
1) "pending"
2) (integer) 1
3) "min"
4) "1793225809941-1"
5) "max"
6) "1793225809941-1"
7) "consumers"
8) 1) 1) "name"
      2) "dr-fairbanks"
      3) "pending"
      4) (integer) 1
# Unacknowledged alerts survive a consumer crash and can be re-assigned with XCLAIM.

R6  DURABILITY SETTINGS - why Redis is a cache here, not the record
==============================================================================
127.0.0.1:6379> CONFIG GET appendonly
1) "appendonly"
2) "no"
127.0.0.1:6379> CONFIG GET save
1) "save"
2) "3600 1 300 100 60 10000"
# With appendonly=no, writes since the last RDB snapshot are lost on a crash. Acceptable for
# holds, caches, counters and alerts (all re-creatable from PostgreSQL); NOT acceptable for
# diagnoses or prescriptions. Production setting for the stream: appendonly yes + appendfsync everysec.
